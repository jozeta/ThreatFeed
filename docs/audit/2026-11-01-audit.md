## Executive Summary

ThreatFeed is in good shape for a hobby-scale, backend-free product. It has 633 passing tests, strict TypeScript, a careful sanitizer and several layers of fallback in the deploy pipeline. I found **no P0 issues** and no exploitable security hole in the shipped configuration.

Its main weakness is **startup and refresh cost**, caused by doing all data work on the main thread over a large payload:

- **Startup download:** every visit, and every 30 minutes after that, downloads a **10 MB snapshot (2.4 MB compressed)**. 5.4 MB of it is full article HTML that is only needed when an article is opened.
- **Main-thread CPU:** on a cold load, the duplicate-story check took **2.8 s of CPU** and story clustering **1.3 s**. Long tasks reached **1.6 s each on a 4× slowed CPU**, 7.3 s in total.
- **Wasted refreshes:** the 30-minute snapshot refresh repeats all of that work even when the snapshot has not changed, including in background tabs.

Other important findings:

- **Gist sync brings deleted items back.** Muted keywords, watchlist terms, saved searches and alert rules removed on one device return after a sync (BUG-001).
- **Non-Latin duplicates.** Different stories with non-Latin titles can be hidden as duplicates; this is reproduced (BUG-002).
- **Dependency advisories:**
  - DOMPurify, the sanitizer, has three published advisories. None applies to how ThreatFeed configures it, but the patch upgrade costs nothing (SEC-001).
  - The dev toolchain (Vite 5, Vitest 2) carries high and critical advisories, and the dev server listens on the whole network (SEC-002).
- **No Content Security Policy** as defence in depth (SEC-003).

The biggest product opportunities, from the competitor research:

- Vendor and product subscriptions with alerts (OpenCVE)
- Shareable digests and static RSS/JSON outputs (Talkback, ransomware.live)
- Per-CVE triage status (CIRCL Vulnerability-Lookup "sightings")

## Application Architecture

**Purpose and users:** an editorial, newspaper-style security news reader with threat-intelligence views (vulnerabilities, ransomware, actors, briefing) and a wall-display "TV" mode. It is for security practitioners, SOC teams and IT admins who want a curated daily read and a lobby or SOC screen. It needs no account and no backend.

**Runtime:** React 18 + TypeScript + Vite 5 + Tailwind 3. It is a static site on GitHub Pages and an installable PWA (`public/sw.js`).

**Data plane:**

```
GitHub Actions (every 30 min, .github/workflows/deploy.yml)
  └─ scripts/build-snapshot.ts (817 lines, jsdom + the app's own parser)
       fetches ~179 feeds, CISA KEV, EPSS, NVD (incremental), GHSA, MSRC, ATT&CK/Malpedia, leak sites, HIBP
       carries history forward by downloading the previously published files
  └─ public/data/*.json → deployed with the app
       snapshot.json 10.2 MB (2.4 MB gz) · vulns.json 2.0 MB · msrc.json 1.7 MB · nvd-cache 1.6 MB · actors 0.4 MB …

Browser
  main.tsx → App.tsx (hash router, useHashRoute)
  SettingsContext  — settings in IndexedDB
  FeedContext (809 lines) — the hub: feeds, articles, health, intel data, refresh orchestration
     init: IndexedDB → feeds.json merge → seed articles → stored articles (re-scored)
     refresh: loadSnapshot() → applyFetched() [merge + dedup + IDB write] → live fetch of uncovered feeds
              through CORS proxies (corsfix → direct → rss2json), 6 workers, flushed ~1/s
     ensure*() loaders: vulns, ransomware, msrc, actors, trends, stats (on demand)
  Views: NewspaperView (clustering, sections, filler), Latest/Unread/My Feed, Briefing, Vulns (7 tabs),
         Ransomware (6 tabs), Bookmarks, Sources, Feed Health, Settings, Reader modal (sanitized HTML)
  TV (lazy chunk): TvShell → TvWall/DashboardWall → useLivingWall (tileEngine), auto reload, breaking news
  Alerts: alertEngine + AlertMonitor (browser notifications), Gist sync (GitHub token in IndexedDB)
```

**Critical paths:**

1. The cold-start pipeline: snapshot fetch, JSON parse, merge, dedup, IndexedDB write, clustering, render.
2. Live feed fetching through third-party proxies.
3. The reader's HTML sanitizing.
4. Gist sync merging.
5. The scheduled snapshot job, which is the single source of truth for the published data.

**Most expensive operations (measured):** `deduplicateArticles` (Jaccard), `clusterArticles`, `computeTrending`, `parseFeedXml`, the JSON parse of the 10 MB snapshot, and sequential IndexedDB get/put per article.

**Likely failure points:**

- Third-party CORS proxies; several feeds fail live (CORS or 403) on every start, as seen in the console.
- A missing or late GitHub scheduled run.
- History files that depend on downloading the previous deploy (guarded).
- Large main-thread tasks on low-end phones.

**Where the implementation differs from what it promises:**

- **"Fast, client-side":** the README presents a lightweight reader, but the cold start moves about 3 MB over the network and does several seconds of main-thread work.
- **"Merge" in Gist sync:** it can't delete; see BUG-001.
- **"Add custom feeds":** a feed added while a refresh is running is not fetched; see BUG-003.

## Functional Bug Report

### BUG-001 [P2] Gist sync brings back keywords, saved searches, folders and alert rules that were deleted on another device

**Category:** Bug
**Confidence:** High (code inspection; documented for rules in a code comment, but users are not told)
**Affected files:** `src/services/sync/gistSync.ts`: `mergeSyncData()`, `mergeAlertRules()`, `union()`
**Problem:** The merge unions `watchlistKeywords`, `stackKeywords`, `mutedKeywords`, `savedSearches`, `bookmarkFolders` and `alertRules` from both devices. A deletion is indistinguishable from "never had it", so anything removed on device A comes back from device B on the next sync.
**Evidence:** `union(local.settings.mutedKeywords, remote.settings.mutedKeywords)`, and the comment "Deletes don't propagate: a rule removed on one device returns from the other."
**Root cause:** The sync stores state, not changes, and keeps no deletion records (tombstones).
**Impact:** A user un-mutes a noisy keyword or deletes an alert rule, and it silently comes back. Rules that send notifications can come back too.
**Recommendation:** Add tombstones: `{ term, removedAt }` lists per collection, merged by the latest timestamp, and purged after about 90 days.
**Implementation approach:**
1. Record `removedAt` when an item is deleted in Settings.
2. Sync a `deleted` map.
3. In the merge, drop any item whose tombstone is newer than its `addedAt`/`updatedAt`.
4. Keep unknown-format remote data backward compatible: no tombstones means today's behaviour.
**Validation:** Add a unit test (TEST-008): device A deletes "deal", device B still has it, and after the merge it is gone on both. Repeat for rules.
**Complexity:** Medium
**Dependencies:** none

### BUG-002 [P3] Different stories with non-Latin titles are hidden as duplicates, and clustering ignores non-Latin words

**Category:** Bug
**Confidence:** High (reproduced)
**Affected files:**
- `src/services/articles/deduplication.ts`: `cleanTitleForComparison()` (`/[^\w\s]/gi`)
- `src/services/articles/clustering.ts`: `extractSignificantTokens()` (`/[^\w\s-]/g`)

**Problem:** `\w` without the `u` flag matches ASCII only. In Japanese, Chinese, Russian, Greek or Arabic titles, everything except embedded Latin words is deleted. Two different stories that share only their Latin words then get a Jaccard similarity of 1.0, and the second one is dropped.
**Evidence:** Reproduced with `npx tsx`:
- `deduplicateArticles([…'Ivanti製品の脆弱性に関する注意喚起', …'Ivantiを狙うランサムウェア攻撃'])` returns only the first.
- `'Уязвимость в Cisco IOS XE'` and `'Атака на Cisco IOS XE завершена'` also return only the first.

**Root cause:** The regexes are ASCII-only.
**Impact:** Lost stories for anyone who adds a non-English feed (the default JPCERT feed is the English one, so default installs are mostly unaffected). Swedish titles keep their words, but accented letters split words ("Sårbarhet" becomes "srbarhet").
**Recommendation:** Use Unicode classes: `.replace(/[^\p{L}\p{N}\s]/gu, '')`. For scripts without spaces (CJK), compare character bigrams instead of words. Treat a title that keeps fewer than 2 tokens as "not comparable".
**Implementation approach:** Change both normalisers, and add a `tokens.size < 2 → skip fuzzy match` guard.
**Validation:** TEST-001 cases for Japanese, Russian and Swedish. Check the dedup counts on the current snapshot before and after; they should be nearly unchanged for English.
**Complexity:** Small
**Dependencies:** best done together with PERF-001

### BUG-003 [P3] A feed added, or an OPML import done, while a refresh is running is never fetched

**Category:** Bug
**Confidence:** High (code inspection)
**Affected files:** `src/context/FeedContext.tsx`: `addCustomFeeds()` calls `refreshFeedsInternal(added)`, which returns at `if (refreshInFlightRef.current || !navigator.onLine) return;`
**Problem:** The in-flight guard drops the request silently. The startup refresh runs for 10–20 s (live fetches through the proxies), and the 30-minute auto refresh takes as long. A feed added in that window shows nothing until the next refresh, up to 30 minutes later.
**Evidence:** Lines around 340 (the guard) and the `addCustomFeeds` body (`refreshFeedsInternal(added)` is not awaited, and nothing is queued).
**Root cause:** The refresh is single-flight and has no queue.
**Impact:** "I added a feed and nothing happened." OPML imports look broken.
**Recommendation:** Keep a pending set of feed ids. When the in-flight refresh ends, run one follow-up refresh for the queued feeds. Show "Queued — will fetch after the current refresh" (UI-009).
**Validation:** Unit-test the queue logic. Manual check: add a feed within 3 s of a page load; its articles should appear when the startup refresh finishes.
**Complexity:** Small
**Dependencies:** none

### BUG-004 [P3] "Due today" / "this week" KEV deadlines use the UTC date instead of the viewer's local date

**Category:** Bug
**Confidence:** High (code); the impact is limited to a few hours a day
**Affected files:**
- `src/components/tv/dashPanels.tsx:234` (`new Date(now).toISOString().slice(0, 10)`)
- `src/services/tv/dashboard.ts` (`kevDue`, `dayKey`)
- `src/pages/vulns/KevTab.tsx:93-101`

**Problem:** CISA due dates are calendar dates, but "today" is computed in UTC:
- In Sweden (UTC+1/+2), between 00:00 and 01:00/02:00 local time, today's deadlines are not highlighted, and yesterday's still count as due.
- In the Americas, the error lasts 4–8 hours every evening.

**Root cause:** `toISOString()` is used as a "local day" key.
**Impact:** A wrong highlight and an off-by-one count on dashboards that run overnight.
**Recommendation:** Add a `localDayKey(date)` helper (`getFullYear/getMonth/getDate`) and use it wherever "today" is compared with a calendar date. Keep UTC for the stats day buckets, which are built server-side in UTC.
**Validation:** A unit test with a fixed clock at 00:30 CET.
**Complexity:** Small
**Dependencies:** none

### PERF-001 [P1] The duplicate check costs about 2.8 s of CPU per cold load and runs twice per merge

**Category:** Performance
**Confidence:** High (profiled)
**Affected files:**
- `src/services/articles/deduplication.ts`: `deduplicateArticles()`
- `src/services/articles/merge.ts`: `mergeFetchedArticles()`
- `src/context/FeedContext.tsx`: `applyFetched()`

**Problem:** Every merge re-runs the fuzzy-title deduplication over the **whole** article list (about 1,900–2,200 articles). Each title is compared with every article in a ±2-day window (about 300), with word sets rebuilt from scratch on every call.

`applyFetched` runs the merge **twice**: once on `articlesRef` to work out the IndexedDB diff, and again inside the `setArticles` updater. Live refreshes flush about once a second, so this repeats many times during a refresh.

**Evidence:** In the profile, `jaccard` has 2.61 s of self time and `deduplicateArticles` 2.83 s inclusive, with 2 call sites per flush.
**Root cause:** The dedup is not incremental (it recomputes the full list for each batch), word sets are not cached, and the candidate search is a linear scan per day bucket.
**Impact:** Several seconds of jank on startup and every refresh, which is worst on phones (1.6 s single tasks at 4× throttle). Input is delayed (poor INP) during refreshes.
**Recommendation:**
1. **Incremental dedup:** dedupe only the incoming items against the existing list, which is already deduplicated, rather than the whole list.
2. **Cache per article:** keep normalised word sets in a `WeakMap<Article, Set<string>>`, or keyed by `id + title`.
3. **Inverted index:** keep a `word → entries` index over the window, so candidates are only articles sharing a rare word. This turns the work from about O(n·w) into about O(n·k), with k ≪ w.
4. **Compute the merge once per flush.**

**Implementation approach:**
- Add `dedupeAgainst(existingIndex, incoming)` that returns the kept incoming items and updates the index.
- Have `applyFetched` call it once and use the result both for state (`setArticles(prev => applyKept(prev, kept))`, a cheap id-based merge that preserves concurrent toggles) and for the DB diff.

**Validation:**
- Re-run the profile script (`shot/profile.mjs`); the dedup time should fall below 100 ms.
- A unit test asserts identical output to the current `deduplicateArticles` on the snapshot fixture (equivalence test).
- A micro-benchmark on 2,000 articles in Vitest.

**Complexity:** Medium
**Dependencies:** BUG-002 (same functions); TEST-001

### PERF-002 [P1] The 10 MB snapshot is downloaded and parsed on every start; 5.4 MB of it is reader HTML

**Category:** Performance
**Confidence:** High (measured)
**Affected files:**
- `scripts/build-snapshot.ts` (writer)
- `src/services/snapshot.ts`: `loadSnapshot()`
- `src/context/FeedContext.tsx` (consumer)
- IndexedDB `articles` store

**Problem:** `snapshot.json` is 10,184,097 bytes raw and 2,441,567 bytes gzipped:
- 1,874 articles take 7.57 MB.
- Of that, **5.40 MB is the `content` field** (full article HTML), which is used only when an article is opened in the reader.

The file is fetched with `cache: 'no-cache'` on every start and every 30 minutes, parsed on the main thread, and every article (with content) is written to IndexedDB on every refresh.
**Evidence:** `curl` sizes of the live site; a breakdown of the local `public/data/snapshot.json` (articles 7,569,233 chars, of which content is 5,401,433; cveIntel 157,685; incidents 527,194).
**Root cause:** One monolithic file carries both the list view and the reader view.
**Impact:**
- About 2.4 MB over mobile data per start and per refresh (the snapshot changes every 30 minutes, so the ETag rarely helps).
- A large JSON parse and structured-clone cost.
- IndexedDB bloat.

**Recommendation:**
1. Split the file into `snapshot.json`, with list fields and a description of at most about 600 characters (expected about 2–2.5 MB raw, roughly 0.6 MB gzipped), and **content shards** such as `content/<yyyy-mm-dd>.json` or per-feed files, fetched by the reader on demand and cached by the service worker.
2. Store content in IndexedDB only for opened or bookmarked articles.

**Implementation approach:**
- In the writer, emit `content` separately and add a `contentRef` per article.
- The reader awaits `ensureContent(article)`, falling back to the description. Bookmarks fetch and pin content.
- Keep the old format readable for one release.

**Validation:** Re-run `perf-audit.mjs`. The transferred snapshot bytes should drop by at least 60%, long-task total should fall, and the reader should open in under 300 ms on a warm cache.
**Complexity:** Medium
**Dependencies:** PERF-005 (IndexedDB writes) benefits too

### PERF-003 [P1] The snapshot refresh reprocesses an unchanged snapshot every 30 minutes, also in hidden tabs

**Category:** Performance
**Confidence:** High (code inspection)
**Affected files:** `src/context/FeedContext.tsx`: the auto-refresh `setInterval` effect and `refreshFeedsInternal()` in the `useSnapshot` branch
**Problem:** In snapshot mode, the default, every interval calls `loadSnapshot()` and then `applyCveIntel` + `applyFetched` for all articles, re-scoring all CVE articles and rewriting everything to IndexedDB. Nothing compares `snapshot.generatedAt` with the one already applied.

The interval also runs while the tab is hidden, so idle background tabs pay seconds of CPU every 30 minutes.
**Evidence:** The effect body has no `generatedAt` comparison and no `document.hidden` check.
**Root cause:** The refresh is time-driven, not change-driven.
**Impact:** Wasted CPU and battery. On a 304 the browser still hands the full cached body to `res.json()`.
**Recommendation:**
- If `snapshot.generatedAt === snapshotGeneratedAt`, skip applying it, but still try the live feeds the snapshot lacks.
- Pause the interval while `document.hidden`. On `visibilitychange`, refresh if the last refresh is older than the interval.
- Better still, fetch a tiny `data/version.json` (`{generatedAt}`) first, and only fetch the big file when it changed.

**Validation:** Unit-test the skip decision. A DevTools Performance trace of an idle tab across an interval should show no long tasks.
**Complexity:** Small
**Dependencies:** none

### PERF-004 [P2] Story clustering takes about 1.3 s and re-runs whenever articles change

**Category:** Performance
**Confidence:** High (profiled)
**Affected files:** `src/services/articles/clustering.ts`: `clusterArticles()`; `src/components/Newspaper/NewspaperView.tsx:326`
**Problem:** For each article, every article in the next 96 hours is compared (about 250–300 candidates), and tokens are recomputed on every call. The memo is keyed on `articles`, which changes on every flush and every read toggle.
**Evidence:** 1.28 s inclusive in the profile.
**Root cause:** A pairwise window scan, no token caching, and a memo dependency that is too broad.
**Impact:** Main-thread jank on the newspaper view (the default tab).
**Recommendation:**
- Use an inverted index (token or CVE → article indices) to find candidates.
- Cache tokens per article.
- Memo on a key of ids and titles (as `App.tsx` already does for search), so read and bookmark toggles don't re-cluster.

**Validation:** Profile under 150 ms; the existing clustering tests stay green.
**Complexity:** Small–Medium
**Dependencies:** none

### PERF-005 [P2] IndexedDB writes are sequential get+put for every article, including unchanged ones

**Category:** Performance
**Confidence:** High (code inspection)
**Affected files:** `src/services/storage/indexeddb.ts`: `saveArticlesToDB()`, `getAllArticlesFromDB()`; `FeedContext.tsx`: the `for (const h of healths) await saveFeedHealthToDB(h)` loops
**Problem:** For each article, `await stateStore.get(id)` and then `await articleStore.put(...)`, one at a time: about 3,800 sequential requests per snapshot apply. Feed health records are written in one transaction each. `getAllArticlesFromDB` sorts with `new Date()` inside the comparator.
**Root cause:** Straightforward but serial code.
**Impact:** Slower refreshes, a longer time to "initialSyncDone", and more chance of transaction contention.
**Recommendation:**
- Read all `articleState` once (`getAll`) into a Map.
- Issue the puts without awaiting each one (a `Promise.all` in one transaction), and skip articles whose stored copy has the same `contentHash`/`updatedAt`.
- Write feed health in one transaction.
- Pre-compute timestamps before sorting.

**Validation:** Time `saveArticlesToDB(2,000)` before and after in the browser (a `performance.mark` around it); expect several times faster.
**Complexity:** Small
**Dependencies:** none

### PERF-006 [P2] All ingest work runs on the main thread

**Category:** Performance
**Confidence:** High
**Affected files:** `FeedContext.tsx`, `services/rss/parser.ts`, `services/articles/*`, `services/intelligence/enrichment.ts`
**Problem:** JSON parse, XML parse, enrichment, scoring, dedup and clustering all share the UI thread. Even after PERF-001 to PERF-004, about 1 s of work per refresh remains on low-end devices.
**Recommendation:** Move "fetch snapshot → parse → merge → dedup → cluster" into a module Web Worker (Vite supports `new Worker(new URL(...), { type: 'module' })` with no new dependency). It posts back the merged list and clusters. `DOMParser` is unavailable in workers, so live XML parsing either stays on the main thread or the snapshot path goes first.
**Validation:** Long-task total during a cold load under 500 ms at 4× throttle.
**Complexity:** Large
**Dependencies:** PERF-001, PERF-002, ARCH-001

### PERF-007 [P2] The service worker keeps every old build's JS and CSS forever

**Category:** Performance
**Confidence:** High (code inspection)
**Affected files:** `public/sw.js`: the `cacheFirst` handling of `/assets/`, and `activate`
**Problem:** Hashed assets are cached on first use and only removed when `CACHE_NAME` changes, which is manual. Every code deploy adds a new `index-*.js` (475 KB), `TvShell-*.js` and other files, so the cache grows without limit on devices that visit often (and TV screens reload on each deploy).
**Recommendation:** On `activate` (or after a navigation), read the current `index.html`, collect the referenced `/assets/` URLs, and delete cached `/assets/` entries not referenced by it or by the lazy chunks loaded since. A simpler option is a separate `assets` cache capped by count (LRU, about 60 entries).
**Validation:** Load, deploy twice, and inspect Application → Cache Storage; only current assets should remain.
**Complexity:** Small
**Dependencies:** none

## Security Report

**Threat model:** a static site with no server-side state. Untrusted inputs are:

- feed XML/HTML, delivered via the snapshot or live through third-party proxies
- imported backups and OPML files
- remote Gist data
- the URL hash parameters

The sensitive asset is the optional **GitHub token (gist scope)** in IndexedDB. The supply chain is npm and GitHub Actions.

**Verified as sound:**
- The reader HTML is re-sanitized at render time (`ReaderModal.tsx:88`).
- URLs go through `safeHttpUrl`.
- `window.open` uses `noopener,noreferrer`.
- Backups are re-sanitized (`sanitizeStoredArticle`).
- Sync data is validated (`cleanRuleList`).
- No secrets are in the repository; workflow secrets are passed through `env`.

### SEC-001 [P1] DOMPurify 3.4.16 has three published advisories

**Category:** Security · **Severity:** Low as configured (npm rates it critical) · **Confidence:** Medium
**CWE:** CWE-79
**Affected component:** `dompurify` (direct runtime dependency), used in `src/services/rss/sanitizer.ts`
**Root cause:** The installed version predates the fixes: SAFE_FOR_TEMPLATES shadow-root bypass, an incomplete IN_PLACE hook fix, and a SMIL `attributeName=href` guard skipped under `application/xhtml+xml`.
**Attack scenario:** All three need configurations ThreatFeed doesn't use (no `SAFE_FOR_TEMPLATES`, no `IN_PLACE`, default `text/html` parser), so I could not construct an exploit against this app. The sanitizer is still the one control between attacker-controlled feed HTML and the DOM, so it should be current.
**Impact if a variant applied:** stored XSS in the reader, which would expose the Gist token (SEC-007).
**Mitigation:** `npm install dompurify@3.4.17` (within the declared `^3.1.7` range; a lockfile change only).
**Verification:** `npm audit` shows no dompurify entry, and the tests pass.

### SEC-002 [P2] The dev toolchain has high and critical advisories, and the dev server is reachable from the network

**Category:** Security · **Severity:** Medium (developer machine only) · **Confidence:** High
**CWE:** CWE-22, CWE-346, CWE-1321
**Affected component:** `vite@5.4.21` (high), `vitest@2.1.9` (critical via tinypool prototype pollution and the UI server), `esbuild` (moderate: any website can read dev-server responses), `tsx`; `vite.config.ts` has `server: { host: true }`
**Root cause:** Major versions behind (Vite 8 and Vitest 5 are current). `host: true` binds the dev server to all interfaces.
**Attack scenario:**
- While `npm run dev` runs, a website you visit can make requests to the esbuild/Vite dev server and read the source.
- Anyone on the same Wi-Fi can reach it, and the path-traversal advisories widen what is readable.

Production is unaffected: these packages are not shipped.
**Mitigation:**
- Remove `host: true`, or use `--host` only when needed.
- Upgrade Vite and Vitest in a dedicated branch (ARCH-006).
- Add Dependabot or Renovate for npm and GitHub Actions.

**Verification:** `npm audit --omit=optional` is clean for the dev dependencies, and `npm run dev` listens on 127.0.0.1 only.

### SEC-003 [P2] No Content Security Policy

**Category:** Security · **Severity:** Low (defence in depth) · **Confidence:** High
**CWE / OWASP:** CWE-693 / A05 Security Misconfiguration
**Affected component:** `index.html`
**Root cause:** GitHub Pages can't send headers, and no `<meta http-equiv="Content-Security-Policy">` is set.
**Attack scenario:** Any future sanitizer gap, or a malicious dependency, can run script, exfiltrate the GitHub token to any origin, and load frames.
**Mitigation:** A meta CSP, for example:

```
default-src 'self'
script-src 'self' 'sha256-…'        (hash the two inline scripts, or move them to files)
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com
font-src https://fonts.gstatic.com
img-src https: data:
connect-src 'self' https://proxy.corsfix.com https://api.rss2json.com https://api.allorigins.win https://api.github.com https: (custom proxy)
object-src 'none'; base-uri 'none'; frame-src 'none'; form-action 'none'
```

The custom-proxy and direct-fetch modes need `connect-src https:`, which is acceptable: the main value is `script-src`.

**Verification:** The app works in all modes with no CSP violations in the console. Inject `<img src=x onerror=…>` through a test feed; it must be blocked twice (sanitizer and CSP).

### SEC-004 [P3] Feed HTML may set `class`, which lets a feed reuse the app's own layout classes to cover the screen

**Category:** Security · **Severity:** Low · **Confidence:** Medium (code inspection; not exploited)
**CWE:** CWE-1021 (improper restriction of rendered UI layers)
**Affected component:** `sanitizer.ts` `ALLOWED_ATTR: [... 'class']`; `ReaderModal.tsx` content container
**Root cause:** Tailwind utilities used elsewhere in the app (`fixed`, `inset-0`, `z-50`, `opacity-0`…) are in the shipped CSS, so feed HTML can opt into them.
**Attack scenario:** A malicious or compromised custom feed (or the proxy, SEC-006) publishes `<a class="fixed inset-0 z-50" href="https://phish.example">…</a>`. When the article is opened, an invisible full-screen link covers the reader, and any click goes to the attacker's page.
**Mitigation:** Remove `class` from `ALLOWED_ATTR`, or allow only a safe prefix (for example `language-*` for code highlighting) via an `uponSanitizeAttribute` hook. Also give the content container `contain: layout paint` or `transform: translateZ(0)`, so `position: fixed` can't escape it.
**Verification:** Add a sanitizer test (TEST-002) that a `class="fixed inset-0"` attribute is stripped.

### SEC-005 [P3] Remote images in articles reveal reading activity to third parties

**Category:** Security / Privacy · **Severity:** Informational · **Confidence:** High
**Affected component:** `sanitizer.ts` (allows `img src`), `ArticleImage.tsx`
**Root cause:** Images load straight from publisher or tracker hosts. Browsers send the origin as referrer (strict-origin-when-cross-origin), and the IP and timing always.
**Attack scenario:** Tracking pixels in feed content record when and from where an analyst read a story (relevant for threat-intel staff reading attacker-adjacent blogs).
**Mitigation:** Add `referrerpolicy="no-referrer"` and `loading="lazy"` through the existing `afterSanitizeAttributes` hook. Add an optional "Load remote images in reader: on/off" setting.
**Verification:** Inspect the image requests: no `Referer` header.

### SEC-006 [P3] Public CORS proxies are trusted with every live feed request

**Category:** Security · **Severity:** Informational · **Confidence:** High
**Affected component:** `services/rss/fetcher.ts` (corsfix, rss2json, allorigins)
**Root cause:** The browser can't fetch most feeds directly.
**Attack scenario:** A proxy operator (or a compromise of one) sees the user's subscription list and can alter feed content: inject links or fake "critical" stories. Script is still sanitized away.
**Mitigation:** Already partly addressed by the snapshot-first default. Document the trade-off in Settings. Offer a one-click deployable Cloudflare Worker proxy template. Mark stories that arrived through a public proxy in the debug view.
**Verification:** n/a (documentation and options)

### SEC-007 [P3] The Gist token is stored in plain text in IndexedDB

**Category:** Security · **Severity:** Low · **Confidence:** High
**CWE:** CWE-312
**Affected component:** `gistSync.ts` (`gistSync` record)
**Root cause:** A client-only app has nowhere safer, and Web Crypto with a non-extractable key would not stop XSS from using it.
**Attack scenario:** Any XSS, or a malicious browser extension, reads the token and can read and write the user's gists. A classic token with `gist` scope covers all of the user's gists.
**Mitigation:**
- Recommend a **fine-grained token** limited to Gists in the UI text.
- Show the token's scopes after a test call (the `X-OAuth-Scopes` header) and warn about broader tokens.
- Add an option "Don't remember token" (keep it only in session memory).
- SEC-003 reduces the risk.

**Verification:** A manual review of the Settings copy and flows.

### SEC-008 [P3] GitHub Actions are pinned to tags, and there is no automated dependency update

**Category:** Security (supply chain) · **Severity:** Low · **Confidence:** High
**Affected component:** `.github/workflows/deploy.yml`, `ci.yml` (`actions/checkout@v4`, `upload-pages-artifact@v3`, `deploy-pages@v4`…)
**Root cause:** Tag pins are mutable. The deploy job has `pages: write` and `id-token: write`, and runs on a 30-minute schedule.
**Attack scenario:** A compromised action tag runs in the build job with the repository's `GITHUB_TOKEN` (read) and `NVD_API_KEY`, and can tamper with the deployed site.
**Mitigation:** Pin the actions to commit SHAs with version comments, and enable Dependabot for `github-actions` and `npm`.
**Verification:** The workflow lint shows SHA pins, and Dependabot PRs appear.

## Architecture and Maintainability

### ARCH-001 [P2] FeedContext is an 809-line hub with about 25 values in one context

**Category:** Architecture · **Confidence:** High
**Affected files:** `src/context/FeedContext.tsx`
**Problem:** Articles, feeds, health, refresh progress, eight datasets and their loaders, the active article and every mutation share one context value. Any change, such as `refreshProgress` once per feed or `activeArticle`, re-renders every consumer, including the newspaper, which then re-checks its memos. The refresh orchestration (about 200 lines) is untestable without React.
**Root cause:** The app grew feature by feature into a single provider.
**Impact:** Wasted renders during refreshes, hard-to-test logic (TEST-003), and higher regression risk for each change.
**Recommendation:**
1. Extract a framework-free `RefreshController` (`services/feeds/refresh.ts`) that owns the snapshot apply, live fetch, flush and queueing (BUG-003), and is unit-testable.
2. Split the contexts: `ArticlesContext`, `FeedsContext` (feeds and health), `IntelDataContext` (the eight datasets), and `RefreshStatusContext` (progress), or one store read through `useSyncExternalStore` selectors.

**Implementation approach:** Incremental: move the code behind the same `useFeeds()` façade first, then switch consumers.
**Validation:** In the React Profiler, the newspaper should not re-render on refresh progress ticks. Existing tests stay green.
**Complexity:** Large
**Dependencies:** enables PERF-006, TEST-003

### ARCH-002 [P3] Very large page components

**Category:** Architecture · **Confidence:** High
**Affected files:** `SettingsPage.tsx` (1,192 lines), `FeedHealthPage.tsx` (1,192), `NewspaperView.tsx` (906), `ReaderModal.tsx` (680), `SourcesPage.tsx` (607)
**Problem:** Hard to review and easy to break. NewspaperView mixes layout, measuring and filling, clustering and toolbar.
**Recommendation:** Split by section, as was already started for `pages/settings/*`. Move NewspaperView's filler and measurement into `Newspaper/StoryFiller.tsx` and its toolbar into `Newspaper/Toolbar.tsx`.
**Validation:** No behaviour change; the tests pass.
**Complexity:** Medium
**Dependencies:** none

### ARCH-003 [P3] No linter, although the code relies on `react-hooks` rules

**Category:** Architecture · **Confidence:** High
**Affected files:** `package.json` (no eslint); 10 files contain `eslint-disable react-hooks/exhaustive-deps`
**Problem:** The hooks rules that the disable comments refer to are never run, so missing dependencies and stale closures elsewhere go undetected.
**Recommendation:** Add `eslint` with `eslint-plugin-react-hooks` (flat config) and `typescript-eslint` (recommended). Run it in CI (TEST-007). Requires approval to add dev dependencies.
**Validation:** `npx eslint src` runs in CI; the first run's findings get triaged.
**Complexity:** Small
**Dependencies:** none

### ARCH-004 [P3] Toolchain several majors behind

**Category:** Architecture · **Confidence:** High
**Affected files:** `package.json`: vite 5→8, vitest 2→5, @vitejs/plugin-react 4→6, jsdom 25→30, TypeScript 5.9→7, React 18→19, Tailwind 3→4, lucide-react 0.460→1.x
**Problem:** Security fixes (SEC-002) and performance improvements are missed, and the eventual upgrade grows harder.
**Recommendation:** Upgrade in stages, in this order:
1. Vite and Vitest (security). Test config is in `vite.config.ts`; check the jsdom env.
2. TypeScript.
3. React 19 (the `inert` prop becomes native, so `App.tsx`'s workaround can go).
4. Tailwind 4 last: it is a CSS-config migration with the largest visual risk, so verify with screenshots.

**Validation:** Tests, build and a visual diff with the existing Playwright scripts at each stage.
**Complexity:** Medium (Tailwind 4: Large)
**Dependencies:** SEC-002

### ARCH-005 [P4] The data history depends on downloading the last deployed site

**Category:** Architecture · **Confidence:** High
**Affected files:** `.github/workflows/deploy.yml`, `scripts/build-snapshot.ts`
**Problem:** Victim history, trends, stats, MSRC, actors and the NVD cache are carried forward by fetching the previous GitHub Pages copy, with Action caches as a second copy. It is well guarded, but the history lives only in a deploy artifact: a bad deploy or a Pages outage can lose or roll back data.
**Recommendation:** Commit the history files to a `data` branch (or attach them to a weekly release) from the workflow, using `contents: write` on a separate job. This gives a durable, versioned history and easy diffs.
**Validation:** Simulate a missing Pages copy; the job restores from the branch.
**Complexity:** Medium
**Dependencies:** none

## UI/UX Report

Verified with screenshots at 1440×900 and 390×844, plus an automated probe for labels, targets, headings and overflow. There is no horizontal overflow at any tested width.

### UI-001 [P2] On a phone, the first headline starts about 520 px down an 844 px screen

**Category:** UI · **Confidence:** High (screenshot)
**Screen:** Newspaper (mobile)
**Problem:** The masthead, category select and Watchlist, search and Filter, view switcher, TV and Mark read, the Trending strip, the "Editorial section edition" toolbar and the section header all come before any news.
**Improved interaction:**
- A compact sticky top bar on mobile: logo, search icon, filter icon.
- The view, TV, Mark read, Sections and Customize controls move into the Filter sheet.
- The masthead shrinks after the first scroll.
- Trending stays as one row.

**Benefit:** Users see three or four stories on the first screen instead of none.
**Implementation:** `Header.tsx` and `NewspaperView.tsx` toolbar: `sm:` breakpoint variants; move the controls into the existing `FilterBar` sheet.
**Acceptance criteria:** At 390×844 the lead headline's top is under 300 px, every control is still reachable in two taps or fewer, and nothing scrolls horizontally.

### UI-002 [P2] The unread count is noise (2,223 on a first visit); there is no "new since last visit"

**Category:** UI · **Confidence:** High (screenshot)
**Screen:** Header stats, Unread tab badge
**Problem:** Everything starts unread, so the badge and the count carry no information. Regular users can't tell what arrived since their last visit.
**Improved interaction:**
- Store `lastVisitAt`.
- Show "37 new since 08:12" and a thin divider in Latest marking where the new items end.
- Offer "Catch up: mark everything older than my last visit as read".
- On the first visit, start the unread baseline at "now − 24 h".

**Benefit:** It answers a returning analyst's first question: what is new?
**Implementation:** `FeedContext` (lastVisitAt in IndexedDB, updated on `visibilitychange` hidden), `NavigationTabs` badge, `NewspaperView`/`ListView` divider.
**Acceptance criteria:** The badge shows only items published or fetched after the baseline. The divider shows at the right place, and one action marks all older items read.

### UI-003 [P2] Watchlist badges appear on most stories, so they no longer stand out

**Category:** UI · **Confidence:** Medium (screenshot: three of three top stories carry badges; the Watchlist counter shows 61)
**Screen:** Article cards, Watchlist filter
**Problem:** The default watchlist includes broad phrases ("remote code execution", "unauthenticated", "Cisco", "Exchange"), so a large share of stories gets a yellow badge, and the badge stops meaning anything.
**Improved interaction:**
- Separate **"My terms"** (user-added: strong badge) from **default topic presets** (subtle text label, no badge).
- In Settings → Watchlist, show how many stories each term matched in the last 7 days, so noisy terms are visible.

**Benefit:** Badges point at what the user actually cares about.
**Implementation:** Store the preset origin per keyword (`upgradeWatchlistKeywords` already knows the defaults); change the `ThreatBadges` rendering; add counts in `IntelligenceSettings`.
**Acceptance criteria:** A fresh install shows strong badges on less than 15% of front-page stories; user terms always show.

### UI-004 [P3] Form fields that rely on placeholders as labels

**Category:** UI (accessibility) · **Confidence:** High (automated probe)
**Screen:** Global search, mobile category select, and in Settings: 4 selects, the keyword inputs, folder name, Gist token and Gist ID
**Problem:** No `<label>`, `aria-label` or `aria-labelledby`. Screen readers announce "edit text" with no name, and the placeholder disappears when typing (WCAG 1.3.1, 3.3.2, 4.1.2).
**Improved interaction:** A visible label (or `aria-label`) for each field.
**Implementation:** Add `aria-label` to the search input ("Search stories") and the select ("Category"). Use `<label htmlFor>` in Settings.
**Acceptance criteria:** The probe reports 0 unlabelled inputs on all pages.

### UI-005 [P3] 39 tap targets smaller than 24×24 px on the mobile front page (26 on Briefing)

**Category:** UI (accessibility) · **Confidence:** High (automated probe)
**Screen:** Article action icons (read, bookmark, share, open), tag chips, small header icons
**Problem:** Mis-taps, and fails WCAG 2.2 2.5.8 (Target Size, minimum).
**Improved interaction:** At least 24 px hit areas (44 px recommended) through padding, without changing the icon size.
**Implementation:** A shared `IconButton` with `min-w-[44px] min-h-[44px] sm:min-w-0 sm:min-h-0`, or pseudo-element hit areas.
**Acceptance criteria:** The probe reports 0 targets under 24 px at 390 px width.

### UI-006 [P3] The page title never changes, and pages have two or three `<h1>` elements

**Category:** UI (accessibility, usability) · **Confidence:** High (probe)
**Screen:** All routes
**Problem:** Every tab and history entry is titled "ThreatFeed — Security Intelligence Daily", and screen-reader heading navigation sees two or three top-level headings.
**Improved interaction:** `document.title = "Vulnerabilities · ThreatFeed"` (or the article title while the reader is open). One `<h1>` per view; the masthead is a non-heading or `<p>` when another page title exists.
**Implementation:** A small `useDocumentTitle(tab, article)` hook in `App.tsx`; adjust the heading levels.
**Acceptance criteria:** Titles differ per tab, and each route has exactly one `h1`.

### UI-007 [P3] Inconsistent number formatting ("2,223 dispatches · 2223 unread")

**Category:** UI · **Confidence:** High (screenshot)
**Screen:** Header stats line, tab badges
**Improved interaction:** Use `Intl.NumberFormat` everywhere (a `fmtCount()` helper).
**Acceptance criteria:** All counts of 1,000 or more show the same grouping.

### UI-008 [P3] Ransomware group slugs shown as names ("Thegentlemen")

**Category:** UI · **Confidence:** High (screenshot, and the snapshot has `"group":"thegentlemen"` ×89)
**Screen:** Trending strip, victim lists, TV tiles
**Problem:** The leak-site data uses slugs, and the UI title-cases them. Readers see wrong names ("Thegentlemen" for "The Gentlemen").
**Improved interaction:** Map slugs to display names from `ransomware.json` group profiles (or the ransomware.live group list) in the snapshot build; keep the slug as the key.
**Acceptance criteria:** Known groups show their published names everywhere.

### UI-009 [P3] Actions during a refresh fail silently

**Category:** UI · **Confidence:** High (code; the user-facing side of BUG-003)
**Screen:** Sources (add feed, OPML import), header refresh button
**Problem:** Refresh or add during a running refresh does nothing, with no feedback.
**Improved interaction:** A toast or inline status: "Refresh in progress — your new feed will be fetched next". The refresh button shows progress instead of being clickable.
**Acceptance criteria:** Every user-started fetch either runs or says that it is queued.

## Feature Recommendations

### FEAT-001 [P2] Product subscriptions: alert when a CVE, KEV entry or EPSS jump hits "my stack"

**Category:** Feature · **Confidence:** High (fits existing data) · **COMP:** COMP-005
**Affected files:** `services/intelligence/alertRules.ts`, `alertEngine.ts`, `cveWatch.ts`, `pages/settings/VulnVendorSettings.tsx`
**User problem:** An admin cares about "anything new for FortiGate, Exchange or Veeam" across news, NVD, KEV and EPSS, not only keywords in headlines.
**Expected value:** The single most-requested CVE-monitoring workflow (OpenCVE is built around it), using data ThreatFeed already has (`stackKeywords`, `vulns.json`, `cveWatch`).
**How others do it:** OpenCVE subscribes to CPE vendors and products and alerts by email or webhook.
**Suggested implementation:**
- Add alert-rule conditions: "new CVE for a stack product with CVSS ≥ X", "stack CVE added to KEV", "stack CVE EPSS rose above Y".
- Evaluate them when `vulns` updates.
- Notify through the existing browser notifications (and FEAT-003).

**Architectural changes:** The alert engine gains a `vulns` source alongside `news`.
**Dependencies:** none. **Complexity:** Medium. **Expected impact:** High.
**Risks:** Noise if product matching is fuzzy; reuse the vendor/product normalisation in `vendor.ts`.
**Acceptance criteria:** A rule "Fortinet, KEV" fires once when a Fortinet CVE is added to KEV, survives a reload without firing again, and is listed in the alert history.

### FEAT-002 [P2] A digest to share: copy or download today's briefing as Markdown, HTML or email text

**Category:** Feature · **COMP:** COMP-002, COMP-003
**User problem:** Analysts paste a daily or weekly summary into Slack, Teams or email by hand.
**Expected value:** It turns ThreatFeed's Briefing into a team artifact at no backend cost.
**How others do it:** Talkback Chronicles and newsletters; Inoreader email digests.
**Suggested implementation:** "Share briefing" on the Briefing page offers Copy as Markdown, Copy as rich text (HTML clipboard), Download .html (print-ready) and an `mailto:` draft. Options: period (24 h / 7 d), sections, top N per section.
**Architectural changes:** A pure `services/intelligence/briefingExport.ts` function (testable).
**Dependencies:** none. **Complexity:** Small. **Expected impact:** Medium–High.
**Risks:** Clipboard API permissions; long mailto URLs (fall back to download).
**Acceptance criteria:** The output pastes cleanly into Slack and Outlook with links intact, and unit tests cover the generators.

### FEAT-003 [P3] Outbound webhooks for alert rules (Discord, Teams, generic)

**Category:** Feature · **COMP:** COMP-005, COMP-003
**User problem:** Alerts only reach a browser that is open on one machine.
**Expected value:** Team notification without a server.
**Suggested implementation:** Per-rule "Send to webhook". POST JSON from the browser.
**Constraints to verify first:** browser CORS support varies. Discord webhooks accept browser POSTs. Slack incoming webhooks generally need `no-cors`/form posts and give no response. Teams workflows differ. A **server-side variant** (rules evaluated in the 30-minute GitHub Action, secrets in repo settings) avoids CORS but only covers the owner's own deployment.
**Dependencies:** FEAT-001 for vulnerability-type rules. **Complexity:** Medium. **Expected impact:** Medium.
**Risks:** The webhook URL is a secret stored in IndexedDB (same class as SEC-007), and endpoints could be spammed if rules are noisy (rate-limit per rule).
**Acceptance criteria:** A test button posts a sample, delivery failures show in the alert history, and there is at most one post per rule per gap window.

### FEAT-004 [P2] Static machine-readable outputs from the snapshot job: RSS and JSON for critical news, KEV additions and victims by sector/country

**Category:** Feature · **COMP:** COMP-002, COMP-004
**User problem:** Teams want ThreatFeed's curated, de-duplicated and scored stream inside their own tools (SIEM, Slack RSS app, another reader).
**Expected value:** It uses the static architecture well: files are generated every 30 minutes at zero runtime cost.
**Suggested implementation:** `build-snapshot.ts` also writes `data/feeds/critical.xml`, `kev.xml`, `ransomware-victims.xml` and JSON equivalents (the top 100 items each). It links them from Sources and adds `<link rel="alternate">` in `index.html`.
**Dependencies:** none. **Complexity:** Small–Medium. **Expected impact:** Medium.
**Risks:** Victim names in public feeds are already public via the leak-site trackers. Keep the same fields ThreatFeed shows, and nothing more.
**Acceptance criteria:** The feeds validate (W3C feed validator), update each run, and stay within size limits.

### FEAT-005 [P3] Saved searches as live "monitoring feeds" with new-item counts

**Category:** Feature · **COMP:** COMP-003, COMP-001
**User problem:** Saved searches exist but must be re-run by hand, and nothing says when they have new results.
**Suggested implementation:**
- Show saved searches as entries in My Feed / the category menu, with a "new since last viewed" count.
- Allow "alert me" to turn one into an alert rule (reusing `ruleForm.ts`).

**Dependencies:** UI-002 (last-visit baseline) helps. **Complexity:** Small. **Expected impact:** Medium.
**Risks:** Index cost; reuse the MiniSearch instance (PERF-010).
**Acceptance criteria:** Each saved search shows a correct count of unseen matches, and opening it clears the count.

### FEAT-006 [P3] CVE timeline in the CVE panel: published → PoC/exploit → KEV → patch → news coverage

**Category:** Feature · **COMP:** COMP-001
**User problem:** "How fast is this moving, and what happened when?" is scattered across badges.
**Suggested implementation:** Use the existing `vulns.json` (KEV dateAdded, NVD published, exploit dates), MSRC data and the article dates for that CVE. Render a horizontal timeline in `CvePanel.tsx`. Add the EUVD ID if it becomes available in the data.
**Dependencies:** none. **Complexity:** Medium. **Expected impact:** Medium.
**Risks:** Missing dates; show only the known events.
**Acceptance criteria:** For a KEV CVE with news, the timeline shows at least three dated events in order.

### FEAT-007 [P3] Per-CVE triage status ("sightings" for one team): Not affected / Investigating / Patched / Exploited here

**Category:** Feature · **COMP:** COMP-006, COMP-005 (custom tags)
**User problem:** Admins track their response to KEV entries in spreadsheets.
**Suggested implementation:**
- A status selector and note on CVE rows and panels, stored in IndexedDB and synced via Gist (with tombstones, see BUG-001).
- A KEV-tab filter "Untriaged in my stack".
- CSV export.

**Dependencies:** BUG-001 (sync correctness). **Complexity:** Medium. **Expected impact:** High for the admin persona.
**Risks:** Scope creep towards a ticketing system; keep it to status plus a note.
**Acceptance criteria:** The status persists, syncs, filters and exports.

### FEAT-008 [P3] Ransomware victim alerts by country and sector

**Category:** Feature · **COMP:** COMP-004
**User problem:** "Tell me when a Swedish or healthcare victim is posted."
**Suggested implementation:** Alert-rule conditions on `incidents.victims` (`country`, `sector`, `group`), evaluated on each snapshot.
**Dependencies:** none (same engine as FEAT-001). **Complexity:** Small. **Expected impact:** Medium.
**Risks:** Leak-site data quality (sector or country missing); show "unknown" honestly.
**Acceptance criteria:** A rule for "SE" fires once per new matching victim.

### FEAT-009 [P4] Optional cluster summaries with a user-supplied API key

**Category:** Feature · **COMP:** COMP-001, COMP-002
**User problem:** Five articles on one incident still take five reads.
**Expected value:** Both AI-heavy competitors lead with summaries. This closes the gap without a backend.
**Suggested implementation:** Off by default. The user pastes their own API key. A "Summarise" button on the ClusterModal sends titles and descriptions only (not full content). The result is cached per cluster id.
**Dependencies:** SEC-003 (CSP `connect-src` for the API host), and the same secret-storage caveats as SEC-007. **Complexity:** Medium. **Expected impact:** Medium.
**Risks:** Cost, privacy (sends headlines to a third party), hallucination (show the sources and a "generated" label).
**Acceptance criteria:** Without a key nothing changes. With a key, the summary cites its articles and appears within 5 s.

## Final Assessment

- **Biggest weaknesses:** startup and refresh cost from processing a monolithic 10 MB snapshot on the main thread, with quadratic-ish dedup and clustering (PERF-001 to PERF-004). Also a central context that makes this logic hard to test (ARCH-001), and sync that can't delete (BUG-001).
- **Most important opportunities:** ThreatFeed already holds the data that commercial tools charge for: KEV, EPSS, NVD, Patch Tuesday, ransomware victims and news, clustered. Turning that into **proactive outputs** is the largest gain per effort:
  - stack alerts (FEAT-001)
  - shareable digests (FEAT-002)
  - static RSS/JSON feeds (FEAT-004)
  - triage status (FEAT-007)
- **Highest-impact fixes:** PERF-003 (small), PERF-001 and PERF-002 (medium), then BUG-001.
- **Features most likely to improve competitiveness:** FEAT-001 (OpenCVE's core) and FEAT-002 (Talkback and Inoreader digests), then FEAT-004 and FEAT-007. None conflicts with the no-backend, no-account principle that sets ThreatFeed apart.
- **Implement first:** Stage 1 in one sitting (SEC-001, PERF-003, BUG-003, BUG-004, SEC-004 with TEST-002), then Stage 2 led by TEST-001 → PERF-001.
